# Dragonwilds Sync — Hidden Web Builder / `.rsdwl` Compatibility Contract

> **Authoritative implementation note for AI/human maintainers.**
>
> This file is intentionally not linked from the public website UI. If work touches the browser World builder, `.rsdwl` profile import/export, Dedicated World creation, or application of a World save, read this entire document first and preserve these rules.

## 0. One-sentence implementation instruction

**The website may author a complete World draft and package an optional user-selected World save into a `.rsdwl`, but browser-generated bundles are untrusted configuration bundles; the desktop application must create fresh local authority/secrets, explicitly import the draft, and safely stage/apply the included save without ever treating the website as an administrator or signing authority.**

---

# 1. Existing authoritative application contracts

Do not invent a second unrelated package format.

Current application authorities include:

- `backend/profile_bundle.py`
  - `.rsdwl` v3 profile bundle
  - format: `dragonwilds-sync-launcher`
  - version: `3`
  - package type: `profile`
  - stable top-level namespaces `/profile`, `/worlds`, `/items`
  - payload SHA-256 records
  - normal application exports use Ed25519 operator signatures
- `backend/profile_store.py`
  - Dedicated World profile creation and persistence
  - `SERVER_PROFILES_DIR`
  - `create_server_profile()`
  - application-generated server/sync credentials
- `backend/world_save_distribution.py`
  - the profile-owned World save snapshot lives at:
    `SERVER_PROFILES_DIR/<profileId>/savegame/`
- `backend/world_operations.py`, `backend/world_maintenance.py`, and server runtime code
  - backup/restore/activation rules

The browser builder must remain compatible with those authorities.

---

# 2. Required trust model

## Normal desktop-authored `.rsdwl`

A normal Dragonwilds Sync v3 profile export remains signed by the desktop application's operator identity.

Do **not** weaken the normal signed import path.

## Browser-authored `.rsdwl`

A static GitHub Pages website has no legitimate access to the user's local Ed25519 operator private key.

Therefore the browser must never pretend to be a trusted operator.

Browser bundles must explicitly declare:

```json
{
  "producer": {
    "application": "Dragonwilds Sync Web Builder"
  },
  "security": {
    "trustMode": "website-draft"
  }
}
```

A browser draft must not contain a forged/fake `operatorSignature`.

The application may support this exact unsigned draft mode only through a **separate restricted validation path**.

Do not change the signed normal importer to "signature optional" globally.

---

# 3. Website-draft acceptance gate in the desktop application

The desktop application may accept an unsigned v3 package only when **all** of the following are true:

```text
format == dragonwilds-sync-launcher
version == 3
packageType == profile
producer.application == Dragonwilds Sync Web Builder
security.trustMode == website-draft
payload index SHA-256 validates
all required payloads exist
all payload sizes and SHA-256 values validate
all paths pass safe_member/path traversal validation
only website-draft allowlisted payload roles are present
no prohibited secret/authority fields are present
```

If any condition fails, reject the file.

A website draft is **configuration input**, not proof of ownership.

---

# 4. Browser-generated `.rsdwl` layout

Use the normal v3 ZIP container with a `.rsdwl` extension.

Recommended layout:

```text
manifest.json
profile/
  profile.json
worlds/
  worlds.json
  drafts/
    <profileWorldKey>/
      server-profile.json
  assets/
    <profileWorldKey>/
      icon.<ext>
      banner.<ext>
  saves/
    <profileWorldKey>/
      ... user-selected World save files ...
items/
  manifest.json
```

If the user drops an already-zipped World save, it may instead be stored as:

```text
worlds/saves/<profileWorldKey>/world-save.zip
```

with payload role:

```text
world-save-archive
```

The desktop application, not the website, owns safe archive extraction.

# 5. Required manifest envelope

Browser-generated bundles should retain the existing v3 envelope shape.

Example:

```json
{
  "format": "dragonwilds-sync-launcher",
  "version": 3,
  "packageType": "profile",
  "packageId": "browser-generated-random-id",
  "createdAtUtc": "2026-08-20T00:00:00.000Z",
  "producer": {
    "application": "Dragonwilds Sync Web Builder",
    "version": "web-v1",
    "fingerprint": "browser-draft"
  },
  "profile": {
    "profileId": "browser-generated-profile-id",
    "profileName": "Example World"
  },
  "layout": {
    "profileRoot": "profile/",
    "worldsRoot": "worlds/",
    "itemsRoot": "items/"
  },
  "payloads": [],
  "security": {
    "digestAlgorithm": "sha256",
    "payloadIndexSha256": "...",
    "exportKey": "...",
    "trustMode": "website-draft"
  },
  "metadata": {
    "charactersIncluded": false,
    "worldsIncluded": true,
    "worldArtworkIncluded": true,
    "worldSaveIncluded": true,
    "websiteDraft": true
  }
}
```

`operatorSignature` is intentionally absent for a website draft.

Payload index hashing must use the same canonical JSON semantics as `backend/rsdwl_packages.py`:

```text
UTF-8 JSON
sort keys recursively
compact separators (, and :)
SHA-256
```

Each payload record keeps:

```text
role
path
mediaType
sha256
size
required
```

# 8. Prohibited browser-generated data

A web-generated `.rsdwl` must never contain or claim authority over:

```text
server_key
share_access_key
Remote Admin credentials
WebGUI passwords/session tokens
operator private key
Ed25519 signing key
Cloudflare/Directory credentials
GitHub token
Steam credential
Nexus credential
machine-local secret references
absolute local filesystem paths
publication ownership/registration credential
existing trusted World fingerprint authority
```

Also do not include `DedicatedServer.ini` containing credentials as a raw browser-authored file.

The desktop application must generate all required local authority/secrets after import.

# 9. World save input on the website

The browser builder supports adding a World save before generating the `.rsdwl`.

The UI should provide both:

```text
Drop World save here
Choose World save files
```

Where browser support permits, directory/folder drops may preserve relative paths.

Also support a user-provided `.zip` World-save archive.

The save is processed locally in the browser only.

Do not upload the World save to GitHub Pages, Cloudflare, telemetry, the public directory, or any third party.

The website should state clearly:

```text
Your save stays in this browser tab and is packaged locally into the .rsdwl.
```

---

# 10. Browser save safety limits

Recommended browser limits:

```text
maximum total selected save bytes: 256 MiB initially
maximum file count: 4096
maximum individual file: 256 MiB
reject empty/invalid selection
```

The desktop importer retains its own independent package limits and must never trust browser-side validation.

Preserve safe relative paths only.

Reject/strip:

```text
absolute paths
../ traversal
Windows drive prefixes
NUL/control characters
empty path components
```

Never use the user's browser-provided filesystem path as a destination path on the desktop.

---

# 11. How the save is represented in `.rsdwl`

For selected raw/folder files:

```text
worlds/saves/<profileWorldKey>/<safe-relative-path>
```

Each receives role:

```text
world-save-file
```

For a selected ZIP:

```text
worlds/saves/<profileWorldKey>/world-save.zip
```

role:

```text
world-save-archive
```

All save payloads must have recorded byte length and SHA-256.

# 13. Never overwrite a World by default

Website-draft import must create a **new local World profile** by default.

Use `create_server_profile()` or the current authoritative equivalent so the application creates:

```text
new profile ID
new server_key
new share_access_key
local runtime identity
local timestamps
safe default access policy
safe port plan
```

Do not adopt browser-supplied IDs as administrative authority.

Browser IDs are provenance/correlation hints only.

---

# 14. Mapping browser draft to Dedicated profile

After `create_server_profile(name)`, load the new profile and copy only allowlisted fields.

Suggested mapping:

```text
web.name                         → profile.name
web.description                  → profile.description
web.community_rules              → profile.community_rules
web.tags                         → profile.tags
web.classification               → normalized profile.classification
web.audience                     → profile.audience
web.platform_compatibility       → normalized profile.platform_compatibility
web.community                    → public-safe profile.community
web.icon                         → profile.icon_b64 / imported profile artwork
web.banner                       → profile.banner_b64 / imported profile artwork
web.runtimeIntent.ue4ss          → profile.auto_ue4ss
web.runtimeIntent.runeschema     → profile.auto_runeschema
web.release_channel              → supported release-channel field
web.placard_background           → supported placard presentation field
```

Do not copy secret fields even if a malicious package contains them.

# 15. Applying an included World save

An included save is staged into the newly-created profile, not directly into an active game directory.

Safe target:

```text
SERVER_PROFILES_DIR/<newProfileId>/savegame/
```

Recommended transaction:

```text
inspect package
↓
validate every save payload/path/hash/size
↓
create new local World profile
↓
stage save under unique temporary directory inside profile root
↓
if archive: safely extract with zip-slip protection and expansion limits
↓
verify staged save is non-empty
↓
atomically promote staged save to profile savegame/
↓
write import provenance metadata
↓
leave World STOPPED
↓
user explicitly launches when ready
```

Do not start the server automatically after import.

---

# 16. Applying a website save to an existing World

If a future UI permits applying the bundle/save to an existing profile, that must be a separate explicit operation.

Required flow:

```text
select target World
↓
verify target is stopped
↓
create backup of existing profile/save
↓
show destructive replacement confirmation
↓
stage and validate incoming save
↓
atomic replacement
↓
verify resulting save exists
↓
record operation/audit entry
↓
allow user to start World
```

Never replace an active World save in-place.

Rollback must be possible if extraction/promotion fails.

---

# 17. Save archive extraction rules in desktop app

For `world-save-archive`:

```text
ZIP only initially
no absolute paths
no .. path traversal
no symlink/device extraction
bounded member count
bounded uncompressed size
bounded compression ratio
no overwrite outside staging root
```

A malicious `.rsdwl` must not be able to write anywhere except its dedicated staging directory.

---

# 18. Artwork from the browser builder

Temporary banner/icon inputs are local browser data.

When **Save World** is pressed, include them inside the `.rsdwl` under:

```text
worlds/assets/<profileWorldKey>/icon.<ext>
worlds/assets/<profileWorldKey>/banner.<ext>
```

The web builder may preview via Data URLs/object URLs, but the bundle stores the original bytes.

The desktop importer rehydrates the artwork into the local World profile.

Do not require the website to host the user's custom artwork.

---

# 19. UE4SS / RuneSchema / platform icon compatibility

The web builder UI may expose trusted built-in icon keys.

Canonical website/application assets should remain locally bundled and referenced by key, for example:

```text

playstation
nintendo
epicgames
ue4ss

```

Do not package copies of built-in logos into every `.rsdwl` unless required for portability.

# 20. What "Save World" means on the website

The website button should be labeled:

```text
Save World (.rsdwl)
```

It means:

```text
collect current builder fields
↓
collect optional local icon/banner
↓
collect optional local World save files/archive
↓
construct v3 website-draft payloads
↓
SHA-256 every payload
↓
build manifest + payload-index digest
↓
write ZIP container locally in browser
↓
download <safe-world-name>.rsdwl
```

No server request is required to build the file.

The World save and artwork remain local to the browser.

# 21. Browser ZIP implementation

Do not rely on a third-party CDN at runtime.

Acceptable implementations:

1. a small audited ZIP writer bundled in the repo, or
2. a pinned vendored ZIP library with its license in the repo.

A STORE/no-compression ZIP is acceptable for initial compatibility because Python `zipfile` can read it.

The resulting file extension is `.rsdwl` even though the container is ZIP.

# 29. World save privacy

This requirement is absolute:

**Selecting a World save in the website builder must not transmit it anywhere.**

No:

```text
fetch()
XHR
Cloudflare upload
GitHub upload
analytics payload
telemetry body
error-report attachment
```

may contain the selected save bytes or filenames beyond what the user explicitly downloads as their `.rsdwl`.

If analytics are ever added, save selection can at most emit a boolean such as `save_attached=true`; never name, size breakdown, content, or path without an explicit separate privacy review.

# 30. Browser-generated secrets

The browser must not generate long-lived server/admin credentials for Dragonwilds Sync.

The app creates those locally during import.

Temporary random IDs used only for package correlation are fine.

# 36. Do not confuse World save with character save

A browser World-builder save is a **World/server save payload**.

It is not a `profile/characters/...` character save.

World save payloads live under:

```text
worlds/saves/<profileWorldKey>/...
```

Character saves retain the existing `/profile/characters/` contract.

# 37. Compatibility rule for current `.rsdwl` v3

Do not create `.rsdw-web`, `.rsdws`, or another extension.

```text
.rsdwl
```
