# Dragonwilds Sync — World Builder Artwork Compatibility Contract

This file is intentionally hidden from public navigation. It is an implementation contract for AI/human maintainers working on the website World Builder, Desktop application, WebGUI, public placards, `.rsdwl` Website Draft import/export, or shared asset packaging.

## 1. Canonical ecosystem artwork

UE4SS and RuneSchema use the exact project-provided artwork. Do not redraw, trace, recolor, invert, substitute a text glyph, hotlink a CDN copy, or maintain a second surface-specific version.

Canonical runtime paths:

```text
renderer/assets/platforms/ue4ss.webp
renderer/assets/platforms/runeschema.webp
renderer/assets/platforms/paks.svg
```

Website deployment copies `renderer/assets/platforms/` to `assets/platforms/`. Desktop, WebGUI, World Builder, public placards, focused placards, Rules/Mods detail UI, and future editors must resolve ecosystem-family artwork from the same canonical registry/path model.

The stable family IDs remain:

```text
ue4ss
runeschema
paks
```

A Website Draft serializes the family ID and mod list, never a machine-specific artwork path. On import/render, the receiving application resolves the canonical local artwork.

## 2. Website theme background artwork

The website uses the project-provided watercolor knight-versus-dragon scene as a subtle full-page background. It is presentation-only and MUST NOT become World/profile metadata.

Canonical deployed theme variants:

```text
website/assets/backgrounds/world-bg-dark.webp
website/assets/backgrounds/world-bg-white.webp
website/assets/backgrounds/world-bg-glass.webp
```

Theme mapping:

```text
dark  -> world-bg-dark.webp
white -> world-bg-white.webp
glass -> world-bg-glass.webp
```

`website/site-visuals.css` is the shared presentation layer. The background must remain faint enough that text/cards retain contrast. Theme switching changes the theme-specific artwork/wash without changing World data.

Do not package these website theme backgrounds into `.rsdwl` Website Drafts.

## 3. World icon and banner selected in the browser

The World Builder may temporarily load a user-selected icon and banner from the local browser. These files:

- remain local to the browser until export;
- must preview immediately in the placard;
- must survive every live placard re-render during that browser session;
- must not be uploaded to Dragonwilds Sync infrastructure merely to preview them;
- are allowed to be packaged into the exported `.rsdwl` Website Draft when selected.

`website/world-builder-local-art.js` is a defensive preview layer. It ensures browser-local Data URL artwork remains visible even if public-directory URL sanitation or a fallback renderer would otherwise remove it.

The `.rsdwl` package records the artwork as payload data and the Desktop import path must validate and stage it as local World artwork. The Desktop application should then persist the imported artwork in its normal per-World storage and rewrite presentation metadata to the application's managed local asset reference.

Never trust a browser-supplied filename as an arbitrary filesystem destination. Use validated package members and application-owned storage.

## 4. Placard banner blend is a cross-surface presentation rule

A World banner is not supposed to look like a rectangular image pasted on top of the placard. It is a visual header that fades into the permanent dark placard body.

All placard renderers should converge on this behavior:

1. banner fills the available header area with `object-fit: cover` or equivalent;
2. banner remains recognizable in its upper/central area;
3. lower portion fades toward transparency/dark card material;
4. an overlay gradient blends the image into the placard body;
5. the body may overlap the faded lower edge slightly;
6. World icon remains visually anchored across the banner/body boundary;
7. custom browser-loaded banners receive exactly the same treatment as built-in banners;
8. horizontal and standard placards preserve equivalent fade behavior.

Website authority for this treatment is `website/site-visuals.css` together with the existing placard CSS.

Desktop/WebGUI implementations do not need identical CSS, but must preserve the same visual semantics instead of presenting an unblended rectangular banner.

## 5. `.rsdwl` Website Draft semantics

Artwork does not change Website Draft trust. A browser-generated `.rsdwl` remains:

```text
security.trustMode = "website-draft"
metadata.websiteDraft = true
```

Artwork or a World save inside the draft does not make it operator-signed or runnable. Desktop must continue through the restricted Website Draft import and Finish World Setup lifecycle.

Recommended artwork roles remain explicit package payload roles such as:

```text
world-icon
world-banner
```

The importer must validate payload hashes, safe archive paths, supported media type/extension, file size limits, and application-owned extraction targets before using the artwork.

## 6. Release verification

A website/app release that touches World artwork is incomplete until maintainers verify:

- Dark, White, and Liquid Glass themes visibly load their corresponding faint site background;
- World Builder icon upload previews immediately;
- World Builder banner upload previews immediately;
- changing another field does not make the selected local artwork disappear;
- banner is visibly blended/faded into the placard body;
- standard and horizontal placards remain readable;
- UE4SS uses the exact canonical UE4SS artwork;
- RuneSchema uses the exact canonical RuneSchema artwork;
- PAKs remains the third mod-family identity;
- browser export still packages selected World artwork without uploading it;
- Desktop import never treats artwork as trust/authority.

If any of these checks fail, the artwork integration is not complete.
