01 · ARCHITECTURE

One experience,
with hard boundaries.

Full, Quick, Headless, and WebGUI paths reuse the same backend authority rather than inventing separate profile truth. Public discovery, gameplay traffic, Sync transfer, and Remote Admin remain distinct trust surfaces.

LOCAL UI

Electron application

The renderer presents Appys and workspaces while privileged mutation crosses bounded preload/IPC and JSON-RPC surfaces. Window settings, scale, startup behavior, themes, and the experimental handheld presentation remain application preferences, not duplicate state stores.

CORE

Profile authority

The trusted Python Core owns Worlds, saves, settings, credentials, imports, backups, manifests, managed files, runtime selections, network configuration, and durable desired state.

WORLD RUNTIME

Supervised ownership

An active hosted World owns its dedicated process, logs, Sync/file-share listener, heartbeat health, publication lifecycle, update/stop transitions, and runtime evidence without becoming a second durable settings writer.

OPTIONAL SERVICES

Directory & WebHost

Cloudflare public presence is sanitized and read-only to visitors. WebHost/Remote Admin is separately authenticated, scoped, CSRF-protected, and never inherits authority merely because the World is public.

02 · AVAILABLE NOW

Current V3 capabilities.

These are implemented source-level contracts in the stable V3 application. Environment-dependent claims still carry the physical acceptance boundaries listed below.

WORLDS & PROFILES

Durable isolated environments

  • Singleplayer, Co-Op, Connected, and Dedicated World/Profile organization
  • Create, detect, adopt, activate, unload, archive, backup, restore, convert, import/export, delete, and recover through Trash
  • Profile-scoped saves, configs, mods, runtimes, routes, presentation, backups, and connected snapshots that cannot hydrate as phantom local Worlds
SYNC & CONNECT

Authenticated client preparation

  • Aggregate, component, and per-mod fingerprints with SHA-256 managed-file identity
  • Changed-payload download, rollback staging, unpack/apply/verify progress, role-correct materialization, and parity proof
  • LAN discovery, Direct Connect, saved Connected Worlds, public-directory handoff, and DragonLink-Connect with synchronized World type
DEDICATED RUNTIME

Server lifecycle control

  • Desired-state validation, start/stop/restart/update, watchdogs, process evidence, backups, and a source-filtered Runtime Console
  • Publication only after the real dedicated process and Sync listener are verified
  • SteamCMD limited to dedicated-server ownership while the retail client remains Steam-owned
MODS & RUNTIMES

Role-aware managed content

  • UE4SS, RuneSchema, and PAK inventory, classification, manifests, load order, provenance, fingerprints, IDs, rollback, and profile assignment
  • Baseline, Stable, Experimental, named, and imported UE4SS/RuneSchema choices with repair/reset/delete/self-heal libraries
  • Archive per-entry client-push selectors so CLIENT/BOTH content can distribute while SERVER_ONLY or distribution: never material stays on the host
LINUX & PROTON

Separated host/client runtimes

  • Ubuntu AppImage desktop package with automated packaged smoke testing
  • Native Linux dedicated-server UE4SS/RuneSchema sources remain server-only
  • Windows and Proton players receive the independently verified Win64 client baseline instead of Linux server loaders
NETWORK & DIRECTORY

Explicit routes and protocols

  • IP-first Direct Connect / World Finder queries use UDP 8422
  • Authenticated Sync transfer uses TCP 27051 plus instance offset; WebHost uses its own TCP listener
  • Signed renewable public heartbeats carry sanitized metadata and require publisher ownership for sensitive directory actions
WEBHOST & REMOTE ADMIN

Separate security surface

  • Opt-in Remote Server access for the active hosted/broadcast World
  • Scoped users, permissions, CSRF protection, rate limiting, audit history, and responsive WebGUI preview
  • Public Server List never receives Remote Admin credentials or administrative authority
CHARACTERS & RSDW-L

Profile-bound game tools

  • Character discovery, profiles, portraits, equipment, inventory, custom items, clone/import/export, starter sharing, and backup-first edits
  • RSDW-L and related tools for items, models, icons, map/player observations, console/spawner surfaces, and optional live bridges
  • Exact discovered saves hand off into the Character Editor without becoming unrelated global state
DESKTOP EXPERIENCE

Persistent and adaptable UI

  • Windows Portable primary package, Ubuntu AppImage, Quick mode, Headless Start, tray/background operation, and safe-graphics recovery
  • Remembered/fixed/maximized window modes, resolution presets/custom sizes, and persistent interface scale
  • Experimental SteamOS/Windows handheld presentation reusing the same Appy navigation and authoritative profile state
03 · CURRENT BOUNDARIES

What automation cannot prove.

Contract checks and packaged smoke tests catch regressions, but they cannot manufacture every real Dragonwilds process, router, GPU, Steam environment, Linux distribution, or multi-machine topology.

Real-game acceptance

CI cannot certify the actual Dragonwilds dedicated process, Steam/SteamCMD behavior, gameplay joining, every telemetry/console bridge, or live game-state semantics. Release claims that depend on the game still require physical tests.

Networks are environment-dependent

Router forwarding, NAT loopback, CGNAT, VPN routing, DNS, UPnP, firewall products, and ISP policy can all change WAN reachability. A healthy directory heartbeat does not prove that a user’s direct route is open.

Linux and Proton breadth

The AppImage and Linux runtime contracts are automated, but real distributions, Proton/Wine versions, permissions, process trees, graphics stacks, and Windows-specific live bridges still need representative hardware acceptance.

Multiple simultaneous hosted Worlds

The ownership model supports independent Worlds, but simultaneous real-game isolation across saves, ports, configuration, update timing, and failure recovery should be proven before it is advertised as universally safe.

Handheld is experimental

The SteamOS/Windows handheld layout exists now, but controller focus, touch behavior, on-screen keyboard flow, docked/undocked scaling, and real-device performance need broader physical acceptance before the project calls it a finished console-style interface.

Updates and recovery

Portable packaging and update contracts are verified in automation; clean-machine behavior, active-worker update recovery, unusual security software, and every failure-time reattachment path still benefit from physical acceptance.

04 · HARDENING DIRECTION

Prove more.
Duplicate less.

The next work is primarily about physical acceptance, resilience, and refining existing V3 surfaces—not creating another competing state model.

HARDEN

Handheld/controller acceptance

The experimental handheld layer is already in the application. The next step is real Steam Deck/SteamOS and Windows-handheld testing, focus polish, keyboard/touch behavior, and controller-first ergonomics.

  • Real controller focus and back-navigation
  • Touch and on-screen keyboard workflows
  • Docked/undocked scale behavior
  • Proton launch/path acceptance on handheld hardware
PROVE

Physical Linux, Proton, and multi-machine workflows

Expand clean-host testing across real Dragonwilds installs, native dedicated hosting, Windows/Proton clients, WAN/VPN routes, and representative Linux distributions.

VALIDATE

Multi-World runtime isolation

Exercise simultaneous hosted Worlds against real save roots, server configuration, ports, process ownership, updates, and recovery before widening operational claims.

REFINE

Recovery and observability

Continue tightening worker recovery, update reattachment, redacted evidence, failure-tail presentation, network diagnostics, and operator-facing release proof.

MAINTAIN

Website and release-source parity

Keep public documentation tied to the canonical application changelog and runtime contracts so the website cannot quietly advertise a retired release or protocol.

05 · RELEASE DISCIPLINE

How changes reach main.

A green build is evidence for one exact commit—not a blanket promise about future changes or unrun physical gates.

  1. 1

    Stage

    Candidate changes land on testing-branch.

  2. 2

    Automate

    Source contracts, backend regressions, authorization checks, real Electron window gates, and package workflows run against the exact commit.

  3. 3

    Exercise

    Applicable package and physical workflows—including real game/network paths—are completed without converting unrun gates into passes.

  4. 4

    Promote

    The coherent candidate reaches stable main, then a tagged release publishes the official assets and checksums.
