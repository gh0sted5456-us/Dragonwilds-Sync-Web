# Dragonwilds Sync — Hidden World Builder Rules / Mods Application Contract

> **Authoritative maintainer note.**
>
> This file is intentionally not exposed in the public website navigation. Read it together with `website/.WEB_BUILDER_RSDWL_COMPATIBILITY.md` before changing World rules, mod-family presentation, `.rsdwl` Website Draft import, public placards, or the corresponding Desktop/WebGUI editor.

---

# 1. Canonical shared preset source

The canonical built-in browser/application preset source is:

```text
resources/world-builder-presets.json
```

Do not maintain unrelated copies of these definitions in:

```text
website JavaScript
Desktop renderer
WebGUI renderer
backend Python
```

A surface may include a small emergency fallback so it remains usable when a resource is missing, but the repository JSON is authoritative and validation should fail if the packaged application omits it.

Current preset format:

```text
dragonwilds-sync-world-builder-presets
version 1
```

---

# 2. Community Rules are structured data plus final text

Do not model Community Rules solely as a display tag.

A World stores both:

```text
preset identity
final editable rules
```

Recommended profile shape:

```json
{
  "community_rule_profile": {
    "id": "normal",
    "label": "Normal",
    "audience": "general",
    "tags": ["General", "Respectful"],
    "rules": [
      "Be respectful to other players and staff.",
      "No griefing..."
    ]
  }
}
```

The existing `community_rules` string remains a compatibility projection:

```text
community_rules = community_rule_profile.rules joined with newline
```

Do not remove `community_rules` until all old import/export/publication paths are migrated.

---

# 3. Canonical built-in rule IDs

Built-in IDs are stable machine keys:

```text
normal
kids
adults
roleplay
custom
```

Do not serialize labels as identifiers.

Correct:

```json
{"id":"kids","label":"Kids / Family Friendly"}
```

Incorrect:

```json
{"id":"Kids / Family Friendly"}
```

Labels may change in future UI revisions; IDs must remain stable unless the schema version changes.

---

# 4. Normal preset

Canonical ID:

```text
normal
```

Audience:

```text
general
```

Purpose:

General public/community World conduct.

Application behavior:

- selectable in World creation/editing
- copies preset rules into the editable rules editor
- host may edit after selection
- if edited away from the exact preset text, presentation should identify the final result as Custom unless the application deliberately supports "Normal · Modified"
- existing Worlds with non-empty legacy `community_rules` and no structured profile import as `custom`

---

# 5. Kids / Family Friendly preset

Canonical ID:

```text
kids
```

Audience:

```text
kids
```

UI label:

```text
Kids / Family Friendly
```

This preset is intentionally stricter about chat/content and protecting minors' private information.

The app must not infer that a server is legally child-directed merely because this preset is selected. This is a host-declared community-rule profile/presentation label.

Public descriptor may expose:

```json
{
  "community_rule_profile": {
    "id": "kids",
    "label": "Kids / Family Friendly",
    "audience": "kids",
    "rules": []
  }
}
```

with the actual sanitized rule strings included when the host publishes them.

# 6. Adults Only preset

Canonical ID:

```text
adults
```

Audience:

```text
adults
```

UI label:

```text
Adults Only
```

The app should clearly present this as an 18+ host-declared community profile.

This does not replace platform/game rules or legal requirements.

# 7. Custom Rules

Canonical ID:

```text
custom
```

When a user edits preset rule text, the safest current behavior is:

```text
preset ID -> custom
final rules -> preserve exactly after normalization/length limits
```

The application may later support:

```text
basePresetId = normal
modified = true
```

but do not introduce this without a schema revision and migration.

# 8. Rule editor behavior across Website / Desktop / WebGUI

All authoring surfaces should behave consistently:

```text
select preset chip
↓
load preset text
↓
show editable rules
↓
user edits
↓
World model updates immediately
↓
placard details chip shows resulting profile
```

Website:

```text
browser-local draft state
```

Desktop:

```text
server profile state in APPDATA
```

WebGUI:

```text
same authoritative server profile through authenticated backend operation
```

WebGUI must not maintain a second copy of World rules.

---

# 9. Placard Community Rules interaction

The back/details face does not need to print every rule directly into the card.

Preferred compact presentation:

```text
COMMUNITY RULES
[ Normal      6 ]
```

or:

```text
[ Kids / Family Friendly      6 ]
```

The chip is clickable.

Clicking it opens a small detail window/dialog containing the actual published rules in order.

For public directory visitors this detail window is read-only.

For Website World Builder / Desktop editor / authenticated WebGUI editor, an Edit action may be available and must update the authoritative draft/profile rather than editing rendered DOM only.

Clicking a Rules chip must not flip the placard itself.

---

# 10. Public Rules safety

Only host-declared public rule text is broadcast.

Do not expose:

```text
moderator private notes
ban evidence
private player identifiers
private Discord channel IDs unless explicitly intended as public
admin credentials
WebGUI data
```

Rule strings require normal public metadata length limits and sanitization.

The website renders text with text nodes/textContent, not remote HTML.

---

# 11. Mod families are first-class categories

Do not flatten all World mods into one untyped display list when family information is available.

Canonical mod-family keys:

```text
ue4ss
runeschema
paks
```

Recommended World profile/public-safe shape:

```json
{
  "mod_groups": {
    "ue4ss": [
      "DragonCore",
      "ProximityLoot"
    ],
    "runeschema": [
      "Extended Resources",
      "Better Capes"
    ],
    "paks": [
      "Example Visual Pack"
    ]
  }
}
```

These are public presentation/runtime-family categories, not executable authority.

# 12. UE4SS family

Canonical ID:

```text
ue4ss
```

Canonical bundled icon:

```text
renderer/assets/platforms/ue4ss.svg
```

The UI chip should use the real bundled UE4SS artwork.

Example:

```text
MODS
[ UE4SS  4 ]
```

Click opens the UE4SS mod names/details.

A UE4SS badge indicates that the World declares UE4SS-family content. It does not, by itself, prove the runtime is currently installed or healthy.

Runtime health remains separate state.

# 13. RuneSchema family

Canonical ID:

```text
runeschema
```

Canonical bundled icon:

```text
renderer/assets/platforms/runeschema.svg
```

The UI chip uses that bundled logo.

Click opens the RuneSchema mod list.

RuneSchema-family metadata must remain separate from UE4SS-family metadata even if one Dragonwilds Sync profile manages both.

---

# 14. PAKs family

Canonical ID:

```text
paks
```

Canonical bundled icon:

```text
renderer/assets/platforms/paks.svg
```

This category covers cooked Unreal package content, including PAK/UTOC/UCAS-oriented packages where appropriate.

Do not infer that every unclassified mod is a PAK.

If an old/foreign World has mods with no known family, retain an internal/public fallback such as:

```text
other
```

and display `Other Mods` until the application can classify them.

Do not silently mislabel unknown content as RuneSchema or PAKs.

---

# 15. Mod-family editor behavior

World Builder/Desktop/WebGUI should provide three primary clickable tabs/chips:

```text
[ UE4SS ] [ RuneSchema ] [ PAKs ]
```

Each opens/activates its own editable list.

The user can add/remove/reorder entries inside each family.

Do not duplicate a mod across families automatically.

If the application scanner knows authoritative runtime family, it may classify scanned content automatically.

Manual user changes should remain possible where classification is ambiguous.

---

# 16. Mod-family placard behavior

On the back/details face, show only categories that contain entries.

Example:

```text
MODS
[ UE4SS  2 ] [ RuneSchema  4 ] [ PAKs  1 ]
```

Each chip is independently clickable.

Clicking `RuneSchema` opens only RuneSchema entries.

Clicking a Mod chip must not flip the placard.

If there are no declared mods:

```text
None published
```

---

# 17. Existing application schema compatibility

Current application server profiles already expose/own useful fields such as:

```text
community_rules
platform_compatibility
auto_ue4ss
auto_runeschema
metadata_cache / mod inventory
```

Migration target:

```text
community_rules                    -> keep compatibility string
community_rule_profile             -> add structured profile
mod_groups                         -> add public/editor grouping
runtime/scanner inventory          -> source authoritative family when known
auto_ue4ss                         -> runtime install intent, not same as mod list
auto_runeschema                    -> runtime install intent, not same as mod list
```

Do not equate:

```text
auto_ue4ss == true
```

with:

```text
mod_groups.ue4ss is non-empty
```

A host can install UE4SS with no custom UE4SS mods, or declare mods before runtime installation is complete.

---

# 18. Recommended Desktop profile migration

When loading a profile:

1. If `community_rule_profile` exists, normalize it.
2. Else if legacy `community_rules` is non-empty:
   - `id = custom`
   - `label = Custom Rules`
   - split normalized newline rules into `rules[]`
3. Else:
   - default new World to `normal`
   - do not silently overwrite an existing old World with new preset text unless the user chooses it.

For mods:

1. If `mod_groups` exists, normalize known families.
2. Else inspect authoritative scanner/inventory metadata.
3. Classify only when reliable.
4. Keep unknown entries as `other` rather than guessing.

# 19. Website Draft `.rsdwl`

The browser draft payload should carry:

```json
{
  "community_rule_profile": {
    "id": "normal",
    "label": "Normal",
    "audience": "general",
    "tags": [],
    "rules": []
  },
  "community_rules": "newline compatibility projection",
  "mod_groups": {
    "ue4ss": [],
    "runeschema": [],
    "paks": []
  }
}
```

The desktop Website Draft importer maps these into the newly-created local World profile after validation.

Do not allow these fields to bring credentials/authority with them.

```text

```

for compatibility during rollout.

# 21. WebGUI requirements

WebGUI uses the same data model and preset resource.

Authenticated World editing should expose:

```text
Community Rules preset chips
editable rule text
UE4SS list
RuneSchema list
PAKs list
```

Writes route through the authoritative backend/profile persistence path.

Do not let WebGUI DOM/local storage become authoritative World configuration.

After save:

```text
Desktop
WebGUI
public descriptor
placard
Website directory
```

must converge on the same normalized profile data.

---

# 22. Runtime worker / subprocess compatibility

The World runtime worker should receive normalized World configuration after the Desktop/controller persists it.

Rules/mod-family presentation data does not give the worker extra administrative authority.

If the worker needs mod-family metadata to build broadcast state, pass the normalized read-only configuration snapshot.

Do not let the website directly command the worker.

Required canonical bundled assets:

# 25. Security tests

Public/browser data must not be able to inject markup through:

```text
rule label
rule text
mod name
mod-family label
```

Render remote text using DOM text nodes/textContent.

Reject or normalize oversized arrays and strings.

Never allow a public mod-family item to provide an arbitrary local asset path.

---

# 26. Final application implementation instruction

When applying this contract to the application:

> Load `resources/world-builder-presets.json` as the canonical preset source. Add normalized `community_rule_profile` and `mod_groups` to Dedicated World profile persistence, preserve `community_rules` as a compatibility projection, classify scanner-known mods into `ue4ss`, `runeschema`, or `paks` without guessing unknown families, expose the same clickable/editable category UI in Desktop and authenticated WebGUI, publish only sanitized public metadata, and make public/focused placards open Rules/Mod-family detail dialogs without changing the card flip state.

Do not close the feature until Website Draft import and an application-created World produce identical normalized Rules/Mods presentation.
